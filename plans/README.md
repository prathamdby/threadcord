## Design decisions settled during review (do not re-litigate)

- **Full pg-boss port** chosen over a Postgres-native patterns-only refactor (operator decision).
- **No web/worker role split**: threadcord is single-process; `schedule`/`supervise` are unconditionally on.
- **No migration advisory lock / no `schema_migrations` table**: migrations stay idempotent statements in `TaskStore.migrate()`, per repo convention; single-process boot makes pr-agent's migration lock unnecessary.
- **No supersession (`superseded_by`)**: threadcord follow-ups are intentional user messages; nothing is stale.
- **No `publish_records` analogue**: Discord progress editing handles its own idempotency.
- **Retention rides the existing janitor `setInterval`**, not a pg-boss cron queue (fewer moving parts; pg-boss's own job tables are cleaned by `supervise` + queue retention options).
- **pr-agent's unused `priority` column is not ported** (known wart in the reference).
- **`TURN_RETENTION_DAYS` uses days**, matching threadcord's `WORKSPACE_TTL_DAYS` convention, not pr-agent's seconds.

## Findings considered and rejected

- Grouped concurrency per repo (pr-agent's `groupConcurrency` per installation): deferred — single-operator deployments don't exhibit the noisy-neighbor problem yet.
- Turn wall-clock timeout (`TURN_TIMEOUT_MINUTES`): deferred — Flue guardrails + operator abort cover hangs today; noted in plan 003 maintenance notes.
- Dropping the `task_followups` table and `initial_turn_started` column: deferred one release for rollback safety; code references are removed in plan 004.
